# PM-Buddy: Invariants

Design contract. A planned constraint/test is not evidence that it exists. Implementation evidence is tracked in [ACCEPTANCE_MATRIX.md](./ACCEPTANCE_MATRIX.md).

| Invariant | Required enforcement | Proof required / phase |
|---|---|---|
| Tenant data is inaccessible without active membership and project scope | Server-resolved context, permission checks, transaction-local context, forced RLS under a non-owner/no-BYPASSRLS runtime role; composite tenant foreign keys | Two tenants, guessed IDs, revoked membership, pooled-connection reuse and absent context; Phase 1 and every new surface |
| Support has no implicit sensitive-data access | Separate expiring support grant, purpose and audit; no default payroll/biometric permission | Grant expiry/revocation and restricted exports; before support rollout |
| Authentication recovery cannot confer approval authority | Expiring single-use verification/reset/invitation tokens; session revocation, MFA and financial permission checks remain required | Token replay/expiry, membership removal, lost device and recovery; Phase 1 |
| Audit history is append-only and redacted | Runtime UPDATE/DELETE/TRUNCATE denied; insert and business mutation in one transaction; explicit safe metadata allowlist | Direct SQL mutation denied; rollback leaves no orphan audit; sensitive values absent; Phase 1 |
| Approval refers to exactly one unchanged snapshot | Expected version, immutable content digest, identity-based maker-checker, step-up MFA and limits | Concurrent approval; changed recipient/rate/amount/allocation invalidates approval; Phase 4 |
| Approved payroll/certificates never mutate | Database state-aware protection and application service; corrections link originals | Direct and API mutation denied; adjustment retains lineage; Phases 4/6 |
| Approved site diaries never mutate; authors cannot approve their own work | Expected versions, independent `quality.manage` reviewer, submitted-content freeze, database lifecycle/actor/locking trigger; unique site/day and composite tenant/project/site reference | `apps/api/test/diaries.e2e-spec.ts` covers API and direct-SQL rejection, concurrency, RLS and project closure; D6.1 web foundation implemented locally |
| Photo evidence is recorded once and never rewritten | Verification computed server-side from the file's own metadata at upload; database CHECK ties `verified` to the location/time checks and keys to tenant/project/photo; insert-only for the runtime role; attach only to draft diaries; unique SHA-256 per project | `apps/api/test/photos.e2e-spec.ts` (direct SQL update/delete/inconsistent insert refused); D6.1 |
| Journal balances in KES minor units | Integer/decimal precision, posting transaction, deferred balancing constraint; immutable entries/lines | Independent golden cases, unbalanced write rejected, no float rounding; Phase 4 |
| Settlements never exceed authorised outstanding | Serialise obligation/reservation row; checked amounts; unique allocations/provider receipts | Concurrent partial settlement/payout and duplicate callbacks; Phase 4 |
| Uncertain external effects cannot be resubmitted blindly | Persisted attempt state and reservation, unique active/uncertain attempt control; reconciliation gate | Crash on both sides of provider call, delayed result and worker retry; Phase 4 |
| Callback acknowledgement means durable intake | Committed inbox before 2xx; unique provider event fingerprint; process repeatably | Queue outage and database outage; Phase 4 |
| Costs are not counted on both accrual and settlement | Unique source/posting purpose; separate committed, incurred and cash dimensions. **Implemented by D5.4:** `cost_entries.measure` separates `accrued` from `paid`, and committed (open LPOs) and cash (incl. VAT) are separate read-model figures; partial unique indexes post each invoice, settlement, expense purpose, count purpose and journal line once; an invoice accrues its net subtotal once (trigger on matched → approved) and each settlement pays only the cost part of its cash, apportioned cumulatively so a fully settled invoice's paid cost equals its subtotal exactly; stock issues re-allocate material cost to BQ items in the report only and post nothing (D-53) | API e2e `spending.e2e-spec.ts` "accrues an approved invoice's subtotal once and posts only the cost part of each settlement; issues re-allocate cost" (accrued 88,000.00 once; settlements 25,862.07 + 62,137.93 = 88,000.00; issuing stock leaves the project total unchanged); domain `settlementCostMinor` tests; Phase 5 |
| Closed periods and historical reports are stable | Effective rule/rate/unit/BQ snapshots; no backdating into closed period | Change current rules and replay report; late attendance creates adjustment; Phases 3–6 |
| Offline events apply at most once | Unique tenant/device/client-event ID with immutable payload fingerprint; per-item durable ack | Multi-day duplicate sync, conflicting payload, app termination; Phase 3 |
| Offline evidence is not silently discarded or overstated | Append-only correction references; optimistic versions; provenance and separate attachment state | Missing attachment, revoked device quarantine, clock/GPS uncertainty; Phase 3 |
| Stock cannot violate approved policy | Ledger transaction locks stock position or equivalent serialisation; tenant-consistent movement references. **Implemented by D5.3:** policy = negative stock is never allowed (D-50). Every movement goes through `app.post_stock_entry`, which locks the `(store, material)` row of `stock_balances` (`SELECT … FOR UPDATE`) in the movement's transaction, re-checks the weighted-average value and refuses a balance below zero; `app.guard_stock_balance` refuses any other balance change and `app.refuse_stock_entry_change` any ledger edit; composite `(tenant_id, …)` keys tie entries to their store, material, BQ item, gang and source line; returns lock their issue and never exceed what is outstanding; deferred triggers check that every posted document has exactly its entries | API e2e `stores.e2e-spec.ts` "never lets two simultaneous issues of the last stock both succeed (API and direct SQL)" (`Promise.all` of two API issues: one 201, one 409 `insufficient-stock`; two concurrent runtime-role transactions: the second waits on the lock and fails), plus the returns, transfers and GRN-void cases in the same file; Phase 5 |
| BQ imports preserve source and totals | Source checksum/mapping/version, validated hierarchy/units/formulas, atomic commit or resumable job | Duplicates, unsupported formulas, partial failure, independent totals; Phase 2 |
| An approved BQ version never changes; later versions come only from approved variations, in one linear history | **D2.3:** API refuses edits and re-import (`bq-not-draft`); `app.guard_bq_version` (approved rows frozen, versions inserted as drafts, a variation version needs its approved parent and `version_no + 1`); D2.2 content triggers (only a draft's bills, sections and items change); `bq_versions_lineage_check`; unique `(tenant_id, parent_version_id)` and `(tenant_id, variation_id)`; no DELETE for `pmb_app` | `variations.e2e-spec.ts` "approves the imported draft as the baseline…" (direct SQL UPDATE of an approved version and its items refused, DELETE denied) and "approves a variation into the next version atomically…"; Phase 2 |
| A variation decision binds to the submitted snapshot, by someone other than its maker | **D2.3:** SHA-256 snapshot digest stored at submission, recomputed and compared at approve/reject (`variation-stale`); base must be the newest approved version; `variation_orders_state_check` (decider ≠ creator and ≠ submitter, reason for rejection); `bq_versions_approval_check`; `app.guard_variation_order` and `app.guard_variation_line` (submitted proposals frozen); step-up MFA for approval | "refuses decisions without the permission, without step-up, by the maker, or on a changed snapshot", stale-on-edit and stale-on-other-approval with rebase; unit tests of the digest and the lifecycle; Phase 2 |
| Concurrent variation approvals cannot both build on one version | **D2.3:** BQ row `FOR UPDATE` in the approval transaction; unique `(tenant_id, parent_version_id)` as the database backstop | "serialises concurrent approvals per BQ: exactly one succeeds" (two variations on one base, and one variation by two approvers); Phase 2 |
| Contract sums are exact and pending variations are never counted as approved | **D2.3:** integer minor units, per-line half-up rounding, VAT once on the subtotal at the snapshotted rate (`packages/domain` `variation.ts`); CHECKs `net = additions − omissions`, `delta = new − base`; revised = newest approved version only | Hand-computed sums to the cent in `variations.e2e-spec.ts` and `variation.test.ts`; Phase 2 |
| A rate build-up used by a BQ item keeps the rate it had when linked | **D2.3:** append-only `rate_buildup_versions` and `rate_buildup_lines` (UPDATE/DELETE revoked), links to a specific version, `app.guard_bq_item_rate_link` (only the unlink stamp changes), one active link per item (partial unique index); line amount CHECK and deferred totals trigger; unit compatibility checked before linking | "keeps a versioned rate build-up library and links BQ items to a version" (direct UPDATE denied, totals mismatch refused, link edit refused); `buildup` unit tests; Phase 2 |
| D2.3 records cannot reference another company's rows | **D2.3:** forced RLS with `WITH CHECK` on every new table; composite `(tenant_id, …)` FKs to project, BQ, version, bill, section, item lineage, instruction, variation and build-up version | "keeps company B out of A's instructions, variations, versions and build-ups" (reads, decisions and composite-FK inserts across companies refused); Phase 2 |
| Unit conversions are exact, explicit and never guessed across dimensions | **D5.1:** `packages/domain/src/materials` exact `BigInt` ratios, one half-up rounding to 6 decimals per result with an `exact` flag; cross-dimension conversions only through supplier, material or attribute factors (resolution supplier → material → attribute → standard); refusals for no path, negative, malformed, over-precise or oversized quantities; same-dimension factors refused (`checkConversionRule`, `app.guard_unit_conversion`, `unit_conversions_check`) | `convert.test.ts` (39 cases with `prices.test.ts`: steel d²/162 vs BS 4449, trips need a factor, supplier shadowing, effective dating, seeded round-trip properties, huge values, float traps); `procurement.e2e-spec.ts` "converts quantities exactly through the API…" and "keeps factors effective-dated…" (direct SQL overlap and edit refused); Phase 5 |
| Price history is append-only and alerts are reproducible | **D5.1:** `material_prices` UPDATE/DELETE revoked for `pmb_app`; corrections are new rows (`corrects_price_id` unique); net/gross, comparable price, previous price, change and the threshold used stored on the row (`material_prices_amount_check`, `material_prices_alert_check`, `app.guard_material_price`) | "records prices, compares them net of VAT per base unit and raises alerts above the threshold" (direct UPDATE/DELETE denied, double correction refused); `prices.test.ts`; Phase 5 |
| Supplier identifiers are encrypted, bound to their row and company, unique by blind index and revealed only with permission | **D5.1:** `FieldCipher` AES-256-GCM with AAD `(tenant, table, column, row)` for KRA PIN, contact phones and bank account numbers; masks only in plain text; unique `(tenant_id, kra_pin_bidx)`; reveal and exact-match lookup need `procurement.manage_suppliers` or company-wide `finance.view_sensitive` (bank: `finance.view_sensitive` only), are rate-limited and audited without values | "stores KRA PINs and phones encrypted, unique per company by blind index, masked unless revealed" (ciphertext copied to another row → 409 `sensitive-value-unreadable`; no plaintext in rows, responses or audit; reveal rate limit); `field-cipher.spec.ts`; Phase 5 |
| Changed supplier payout details are unusable until someone independent verifies them | **D5.1:** immutable `supplier_payout_versions`; a proposal supersedes the current version; only `verified` is `usableForPayment`; contributors (proposer, writer, recent contact-phone changers) kept by `app.guard_payout_version` / `app.record_contact_phone_change`; `supplier_payout_versions_state_check` (no contributor decides); decider = signed-in user; one current version (partial unique index); supplier row lock + `replaces` | "requires an independent verification of payout details (maker-checker in the API and the database)" (self-verification refused by API and CHECK, decision for someone else refused, phone-change contributor refused, concurrent verifiers: one wins, stale proposal 409); Phase 5 |
| D5.1 records cannot reference another company's rows | **D5.1:** forced RLS with `WITH CHECK` on all nine tables; composite `(tenant_id, …)` FKs between materials, conversions, prices, suppliers, contacts and payout versions | "keeps company B out of company A's catalogue and suppliers (API, RLS and composite keys)"; Phase 5 |
| A supplier invoice is approved and paid only against a passing, current three-way match | **D5.2:** `threeWayMatch` (`packages/domain`) run in the submission transaction and stored as append-only evidence; approval refused while the latest match fails (`match-not-passing`) or is stale (new GRN set, other approved invoices, content version or settings: `match-stale`); `invoice_payables` binds the approval to one match, the invoice content version and a verified payout version; `app.invoice_match_violations` and `app.guard_invoice_payable` repeat the quantity, price, total and eTIMS rules in SQL; exceptions only for exceptable reasons, by an independent approver | `procure-to-pay.e2e-spec.ts` "blocks bad payments: a mismatched invoice is not approvable, in the API or in SQL", "matches a corrected invoice; a new GRN makes the match stale…", "prevents double billing…"; domain `match.test.ts`; Phase 5 |
| Procurement decisions are never made by someone who prepared the record | **D5.2:** `contributors` arrays on requisitions, RFQs, LPOs and invoices, kept by triggers (only grow); the decider of a requisition, LPO, single-source exception, match exception or invoice approval is never a contributor; a settlement is never recorded by the invoice's approver; deciders must be the signed-in user; step-up for LPO approval, invoice exceptions, approvals and settlements | "raises requisitions…; decisions are maker-checked in the API and the database", "approves LPOs independently with step-up…", settlement tests (direct SQL as `pmb_app` refused); Phase 5 |
| Supplier settlements never exceed the outstanding balance and are recorded once | **D5.2:** `app.guard_invoice_settlement` locks the payable, requires a current verified payee, an approver ≠ recorder, a date between the invoice date and today, and amount ≤ outstanding; unique `(tenant_id, idempotency_key)` with a request digest; external reference unique per method; append-only; the invoice status follows the settled total | "records settlements idempotently up to the outstanding balance; a payee change stops payment"; Phase 5 |
| A delivery is recorded at most once and its evidence never rewritten | **D5.2:** client-chosen GRN ID + unique `(tenant_id, idempotency_key)` with a request digest (replay returns the original; changed payload or ID reuse refused); GRNs, lines, photos, quotations, matches and documents append-only (a GRN is only voided with a reason, never under an approved invoice) | "records GRNs idempotently with photos, geofence and vehicle checks"; Phase 5 |
| D5.2 records cannot reference another company's rows | **D5.2:** forced RLS with `WITH CHECK` on all 17 tables; composite `(tenant_id, …)` FKs between projects, sites, materials, suppliers, payout versions and every procurement record | "keeps companies apart, denies the unpermitted and keeps amounts and identifiers out of the audit log"; Phase 5 |
| A frozen schedule baseline never changes, and its items are complete | **D6.2:** `schedule_baselines` and `schedule_baseline_items` are append-only: `pmb_app` has no UPDATE or DELETE, and `app.reject_history_mutation` refuses both even for the schema owner; items can be inserted only in their baseline's own transaction (`app.guard_schedule_baseline_item`: the baseline's database-stamped `created_at` must equal `now()`); a deferred constraint trigger checks the item count at commit; numbers increase by one per project under the project row lock; re-baselining appends a new current baseline (the newest) and keeps the old ones | `schedule.e2e-spec.ts` "freezes a baseline that SQL cannot change, and shows variance in working days" (runtime-role UPDATE/DELETE/late INSERT refused; schema-owner UPDATE/DELETE refused by the trigger); Phase 6 |
| The schedule network never contains a cycle | **D6.2:** `dependencyCreatesCycle` (`packages/domain`) in the API before every insert, and `app.reject_schedule_cycle` (reachability from the successor, serialised on the project row) in the database; predecessor and successor are fixed for a dependency's life; CPM refuses a cycle rather than computing dates | Domain `schedule.test.ts` (cycle detection); `schedule.e2e-spec.ts` "refuses cycles in the API and in SQL…"; Phase 6 |
| Schedule variance and percent complete are never invented | **D6.2:** variance is null ("unavailable") without a baseline or for items added after it, never 0; percent complete is physical progress with a declared basis (whole-percent estimate or quantity ÷ total), 100 % exactly when an actual finish exists (CHECK), nothing before an actual start, no future actual dates (trigger, Nairobi business date); project progress is duration-weighted and null when an activity in progress has no reported percentage | Domain `schedule.test.ts`; `schedule.e2e-spec.ts` variance and progress tests; Phase 6 |
| The delay log is append-only | **D6.2:** every change or withdrawal of a delay appends the next version (`supersedes_id` unique, so history cannot branch; version and number checked by `app.guard_schedule_delay`); affected-activity rows are written only with their version; no UPDATE or DELETE for `pmb_app` and a trigger refusal for everyone; an activity a delay names cannot be deleted | `schedule.e2e-spec.ts` "keeps a versioned, append-only delay log…"; Phase 6 |
| D6.2 records cannot reference another company's rows | **D6.2:** forced RLS with `WITH CHECK` on all seven schedule tables; composite `(tenant_id, …)` FKs to projects, milestones, WBS nodes, BQ items (approved version of the same project, trigger), site diaries (same project) and between schedule rows | `schedule.e2e-spec.ts` "isolates companies (RLS) and keeps closed projects read-only"; Phase 6 |
| The cost ledger is append-only; corrections are approved reversals | **D5.4:** `app.refuse_cost_entry_change` (UPDATE/DELETE) and a TRUNCATE trigger on `cost_entries`, UPDATE/DELETE revoked from `pmb_app`; `app.check_cost_entry` validates every insert against its source row and state and stamps `recorded_at`/`business_date` in the database; a reversal journal line names one entry (unique `reverses_entry_id`, never a reversal itself), carries its tags and the opposite amount, and posts only when a second `finance.manage` holder (not the proposer, step-up) approves | API e2e `spending.e2e-spec.ts` "keeps the cost ledger append-only: corrections are reversal journals, maker-checked and posted once" (direct UPDATE/DELETE refused under the runtime role; reversal posts once; reversing a reversal 409 `entry-is-reversal`); Phase 5 |
| A petty-cash float never goes negative | **D5.4:** every balance change is a `petty_cash_entries` row posted by `app.post_float_entry`, which locks the float (`FOR UPDATE`) and refuses a balance below zero or a top-up above the limit; `app.guard_petty_cash_float` refuses any other balance change; `balance_minor ≥ 0` CHECK; the API locks the float before checking; expenses are idempotent (client ID + `Idempotency-Key` + digest) | API e2e "runs a petty-cash float…": `Promise.all` of two spends that together overdraw: one 201, one 409 `float-insufficient`; direct SQL balance edits refused; replay returns the original and a changed payload 409; Phase 5 |
| An M-Pesa SMS never confirms a payment, and one M-Pesa transaction is recorded once | **D5.4:** `parseMpesaSms` returns a draft with `confirmsSettlement: false` and a masked phone; the text is not stored; the expense records `parsed_from_sms` + kind only and still needs a receipt and an independent approval; `petty_cash_expenses_one_mpesa_code` (unique among expenses not rejected) and the API's duplicate lookup across expenses, settlements and top-ups; alerts flag the same code or reference on two payments | Domain tests (`spending.test.ts`, EN/SW synthetic messages); API e2e: SMS draft, `mpesa-code-duplicate` 409, the parser naming the duplicate; Phase 5 |
| Spending approvals are never made by the maker | **D5.4:** expense approval: not the recorder and not the float's custodian, with a receipt; top-up: approver ≠ requester, payer ≠ approver (step-up); count: not the counter and not the custodian; budget: approver not a contributor, on the submitted digest; journal: approver ≠ proposer — repeated by `app.guard_*` triggers; every record's `permissions` flags use the same rules | API e2e: 403 `maker-checker` cases for top-ups, expenses, counts, budgets and journals; Phase 5 |
| D5.4 records cannot reference another company's rows, and portal roles never read spending | **D5.4:** forced RLS with `WITH CHECK` on all 14 spending tables; composite `(tenant_id, …)` FKs to projects, sites, BQ items, cost codes, suppliers, invoices, settlements, floats, expenses, counts and journal lines; explicit reader sets (`SPENDING_READ_PERMISSIONS`, `PETTY_CASH_READ_PERMISSIONS`) that clients, suppliers and consultants never hold | API e2e "keeps clients, suppliers, site agents and other companies out of spending records" (403 for client and supplier, 404 and zero rows for another company, no amounts/codes/payees in audit metadata); Phase 5 |
| Unverified legal rules cannot drive production calculations | Effective-dated rule approval with source/reviewer; production fail-closed gate | Missing/unapproved/expired rule rejected; Phases 2–4 |
| Restore never blindly repeats external money movement | Payment pause persisted outside replayable work; post-restore provider reconciliation before worker resume | Coherent DB/object/key restore and controlled reconciliation; first financial phase |
| Notifications cannot change payment outcome | Separate notification job/idempotency domain | SMS failure retries only notification after confirmed payment; Phase 4 |

Each later migration must identify the invariant it enforces and add a negative/concurrent integration test using the real runtime role. Redis locks and UI disabling are not correctness boundaries.
